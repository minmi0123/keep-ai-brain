# 변경 검토 위험 체크리스트 (비판 세션용)

> 언제 읽나: AI 나 사람이 만든 변경(diff)을 비판적으로 검토할 때, 개발 전에 "이 기능에서 무엇을 조심할지" 볼 때.

**먼저 볼 주의**
- **지적에는 근거가 필수다.** 파일:줄 또는 재현 방법이 없는 지적은 버린다. 지적마다 패턴 번호(C01 등)를 붙인다
- **diff 가 만든·건드린 것만 지적한다.** diff 밖의 기존 문제는 "참고 — 기존 문제" 로만
- **기계가 잡는 것은 보지 않는다.** 스타일·포맷은 린터·정적 분석이 본다. 여기서는 업무 로직·데이터·보안만
- 패턴은 **신호**일 뿐 판정이 아니다. 신호가 보이면 실제로 같은 모양인지 확인한 뒤 지적한다
- **지금은 일반 예시다.** 이 프로젝트에서 실제로 난 버그가 쌓이면 5장대로 바꿔 간다 — 실제 버그에서 뽑은 패턴이 훨씬 잘 잡는다

## 0. 검토 순서

| # | 할 일 |
|---|---|
| 1 | 바뀐 화면·API·함수의 **영향 범위**를 뽑는다 (호출하는 쪽, 그 테이블을 쓰는 쪽) |
| 2 | **형제 찾기** — 고친 로직의 복사본이 있는지 본다(H03). 비슷한 이름의 함수·쿼리, 같은 계산 |
| 3 | 아래 **빠른 검색 표**를 diff 의 추가·수정 줄에 돌린다 |
| 4 | 이슈 대장을 켰으면 그 기능의 기존 이슈를 확인한다 |
| 5 | C → H → M 순으로 패턴을 대조하고 지적을 쓴다 |

## 1. 빠른 검색 표

diff 의 추가·수정 줄에 이 문자열이 보이면 해당 패턴을 먼저 본다.

| 보이면 | 먼저 볼 패턴 |
|---|---|
| `price`·`amount`·`total`·금액 이 요청 본문(request body·params)에서 옴 | C01 |
| 새 API·라우트, `@GetMapping`·`router.` 등 진입점 추가 | C02 |
| `log.`·`console.log`·`print` 근처에 사용자 객체·전화·이메일·카드 | C03 |
| 문자열 더하기·템플릿으로 만든 SQL (`"... WHERE x = " +`, `${}` in SQL) | C04 |
| 한 함수 안에 INSERT/UPDATE/DELETE 가 둘 이상 | C05 |
| `= NULL`·`<> NULL`·`!= null` 비교, `NOT IN (서브쿼리)` | H01 |
| 새 `INNER JOIN`·`JOIN` 이 목록 쿼리에 추가 | H02 |
| 복사해 붙인 듯 비슷한 블록, `_v2`·`_new`·`Copy` 이름 | H03 |
| 빈 `catch`, `catch (e) { log }` 후 계속 진행, `except: pass` | H04 |
| `UPDATE`·`DELETE` 에 WHERE 없음, 키 일부만 조건 | H05 |
| 날짜 비교 `>`·`<=`, `BETWEEN`, 종료일 `23:59:59` | H06 |
| `createdBy`·`userId`·`regId` 를 요청에서 받아 저장 | H07 |
| 반복문 안의 쿼리·API 호출 | M01 |
| 목록 쿼리에 `ORDER BY` 없음, 페이지 크기 제한 없음 | M02 |
| 화면에 숫자·날짜를 직접 문자열로 출력 | M03 |

## 2. CRITICAL — 돈·개인정보·권한 (하나라도 있으면 머지 보류)

| # | 패턴 | 왜 위험한가 | 확인할 것 |
|---|---|---|---|
| C01 | **금액을 클라이언트 값으로 믿음** | 요청을 조작하면 1원 결제가 된다 | 서버가 DB 의 가격으로 다시 계산·대조하는가 |
| C02 | **권한 검사 빠짐** — 로그인만 보고 "내 것인지" 안 봄 | 남의 주문·정보를 id 만 바꿔 본다 | 대상의 소유자 = 로그인 사용자 조건이 쿼리나 서비스에 있는가 |
| C03 | **개인정보가 로그·응답·에러 메시지로 나감** | 로그는 오래 남고 많이 본다 | 마스킹, 응답 DTO 에 필요한 필드만 있는가 |
| C04 | **SQL 을 문자열로 조립** (인젝션) | 입력 한 줄로 데이터 유출·삭제 | 바인딩 파라미터(`?`·`#{}`)인가. 정렬 컬럼 같은 건 허용 목록으로 |
| C05 | **여러 쓰기가 한 트랜잭션이 아님** | 중간 실패 시 반만 반영 (돈은 빠졌는데 주문 없음) | 트랜잭션 경계, 롤백 조건(체크 예외 포함), 외부 호출은 트랜잭션 밖 |

## 3. HIGH — 데이터 정합·상태 (근거 확인 후 수정 요구)

| # | 패턴 | 왜 위험한가 | 확인할 것 |
|---|---|---|---|
| H01 | **NULL 비교 실수** — `= NULL`, `NOT IN` 에 NULL 섞임 | 조건이 늘 거짓/참이 되어 제한이 무력해진다 | `IS NULL`, `NOT EXISTS`, NULL 이 들어올 수 있는 컬럼인가 |
| H02 | **INNER JOIN 으로 행이 빠짐** | 짝이 없는 신규·예외 데이터가 목록에서 사라진다 | LEFT JOIN 이 맞는가, 0건·짝 없음 입력을 시험했나 |
| H03 | **복사본 한쪽만 고침** | 같은 버그가 다른 화면에 그대로 남는다 | 형제 찾기 결과, 같은 계산을 하는 곳 |
| H04 | **예외를 삼킴** | 실패했는데 성공으로 보이고 데이터가 반쯤 남는다 | catch 뒤 롤백·재던지기·사용자 알림 |
| H05 | **WHERE 가 없거나 키가 모자란 UPDATE/DELETE** | 한 줄 고치려다 전체가 바뀐다 | 기본키 전부가 조건에 있는가, 영향 행 수 확인 |
| H06 | **시간 경계 실수** — `>` vs `>=`, 종료일 00:00 | 마지막 날·경계 시각 데이터가 빠지거나 두 번 잡힌다 | 경계값 바로 아래·딱 경계 입력, datetime 끝 날짜 |
| H07 | **등록자·수정자를 요청값으로 저장** | 남의 이름으로 기록된다 | 로그인 정보(세션·토큰)에서 가져오는가 |

## 4. MEDIUM — 표시·집계·성능 (지적하되 머지 보류 사유는 아님)

| # | 패턴 | 왜 문제인가 | 확인할 것 |
|---|---|---|---|
| M01 | **반복문 안의 쿼리·호출** (N+1) | 데이터가 늘면 느려진다 | 한 번에 가져오기(IN·JOIN·배치) |
| M02 | **정렬·페이지 제한 없는 목록** | 순서가 매번 다르고, 큰 데이터에서 멈춘다 | `ORDER BY` + 고유 키, 최대 건수 |
| M03 | **표시 형식 직접 처리** | 천 단위·시간대·소수점이 화면마다 다르다 | 공용 포매터를 쓰는가 |

## 5. 이 문서 갱신

| 언제 | 어떻게 |
|---|---|
| kb 에 이슈가 쌓였을 때 (이슈 대장 `ops/issues.md`) | 반복되는 모양을 묶어 새 패턴으로. 패턴마다 대표 이슈 링크 1~3개 |
| `/critic` 시험 모드에서 놓친 버그 | 그 버그의 코드 신호를 1장 표와 해당 패턴에 더한다 |
| 한 번도 안 걸리는 일반 예시 | 이 프로젝트와 상관없으면 지운다 (읽는 양만 늘린다) |

- 새 패턴 기준: 실제로 2번 이상 났거나, 한 번이라도 돈·개인정보·권한 사고였던 것
- 문서가 30KB 를 넘으면 심각도별로 나눈다
