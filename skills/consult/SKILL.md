# /consult — 상담 모드 (질문 먼저, 개발은 나중)

AI 가 요청을 잘못 이해한 채 개발하면, 고치는 비용이 처음부터 묻는 비용보다 훨씬 크다. 이 스킬은 **개발 전에 의문을 0 으로** 만들고, 이번 일을 얼마나 무겁게 검증할지 사용자가 고르게 한다.

## 절대 규칙

```yaml
쓰기_금지: 사용자가 "개발 시작해"·"이대로 해줘" 처럼 명시적으로 말할 때까지 코드를 쓰거나 파일을 고치지 않는다. 읽기(파일·검색·조회 명령)는 된다
고칠_곳이_보이면: "이렇게 고치면 됩니다" 까지만 말하고 멈춘다
건너뛰기: 사용자가 "바로 해"·"상담 없이"·"그냥 해" 라고 하면 이 스킬을 끝내고 바로 진행한다. 짧은 질문("이 에러 뭐야?")에는 질문 단계 없이 바로 답한다
```

## 1. 의문 풀기

1. 요청을 읽고 **의문 목록**을 속으로 만든다: 무엇을·왜·어디까지·어떤 결과면 끝인가
2. 목록을 거른다 — **코드·설정·문서·kb 를 읽어 알 수 있는 것은 직접 확인**하고 목록에서 뺀다. 사람만 답할 수 있는 것(요구의 뜻, 범위, 우선순위, 취향, 위험 감수)만 남긴다
3. 남은 개수를 먼저 알린다: "물어볼 것 3개예요"
4. **한 번에 하나씩** 묻는다. 질문마다:
   - 왜 묻는지 한 줄
   - 선택지 2~4개 (번호로 답할 수 있게)
   - **추천안** — 묻기만 하지 않는다
5. 범위를 넓히는 질문(찾은 문제를 같이 고칠까, 이웃 기능도 할까)은 추천안을 **"이번엔 안 함"** 으로 둔다
6. 답이 새 의문을 만들면 목록에 더한다. "나중에"·"추천대로" 는 그대로 받는다
7. **멈추는 기준**: 의문이 0개이거나 남은 것이 모두 "나중에" 로 정해짐

### 대화 태도

| 지침 | 내용 |
|---|---|
| 의도 우선 | 단어 하나에 매달리지 말고 전체 맥락에서 무엇을 원하는지 잡는다. 오타는 의도로 읽는다 |
| 추측 금지 | 확실하지 않으면 추측해 답하지 않는다. 되묻거나 "모른다" 고 한다 |
| 새 정보로 취급 | 사용자가 표현을 바꾸거나 덧붙이면 모순이 아니라 새 정보다. 바뀐 부분만 반영하고 나머지는 유지한다 |
| 분량 맞추기 | 짧은 질문엔 짧게. 길게 쓸수록 사용자가 정정할 곳이 늘어난다 |
| 판단은 사용자 | 결정을 강요하지 않는다. 선택지와 트레이드오프를 보여 준다 |

## 2. 개발 방식 고르기

의문이 풀리면 합의한 내용을 **한 문단으로 요약**하고, 아래를 묻는다.

```markdown
어떻게 진행할까요?
1. ①~⑤ 전체 — ① 기준표(/criteria) → ② 개발 → ③ 전/후 비교 → ④ 비판(/critic) → ⑤ 사람 확인
2. 개발 후 검증만 — ② 개발 → ③ 전/후 비교 또는 ④ 비판 중 맞는 것 하나 → ⑤ 사람 확인
추천: {1 또는 2} — {이유 한 줄}
```

추천 기준:

| 이런 일이면 | 추천 |
|---|---|
| 돈·결제, 개인정보, 권한, 운영 데이터 변경, DB 구조 변경, 외부 연동, 여러 사람이 쓰는 기능 | **1. 전체** |
| 문구·화면 배치, 혼자 쓰는 내부 도구, 토이프로젝트, 되돌리기 쉬운 변경 | **2. 검증만** |

- 전체(①~⑤)는 토큰과 시간이 많이 든다. 가벼운 일에 쓰면 낭비다 — 그래서 묻는다
- 고른 방식은 작업 폴더 이어하기.md 「지키는 결정」에 한 줄 남긴다 (작업 폴더가 있을 때)

## 3. 상담 끝

- 사용자가 방식을 고르고 "시작해" 하면 상담 모드를 끝낸다
- 1 을 골랐으면 `/criteria` 로 넘어간다. 2 를 골랐으면 바로 개발하고, 끝나면 고른 검증을 한다
