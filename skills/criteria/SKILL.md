# /criteria — ① 판정 기준표

같은 AI 가 쓰고 같은 AI 가 비판하면 놓치는 곳도 같다. 그래서 **구현 전에 사람이 승인한 "입력 → 기대 결과"** 를 검증의 기준으로 둔다. ③ 전/후 비교와 ④ `/critic` 이 이 표를 읽는다.

참고: 1장(의도 — 문제·기대 결과·영향·제약·미해결 질문)은 Anthropic 「AI-native SDLC 플레이북」(Louis Claxton, 2026-08-21, https://claude.com/ko/resources/articles/the-ai-native-sdlc-playbook)의 `intent.md` 를 따랐다. 2장 "잴 수 있는 완료 기준" 은 그 글이 4단계(Test)에 두는 검증 가능한 목표를 구현 전으로 당겨 온 것이다.

전체 흐름: ① 기준표(이 스킬) → ② 개발 → ③ 전/후 비교 → ④ 비판(`/critic`) → ⑤ 사람 확인. 가벼운 일이면 `/consult` 에서 "개발 후 검증만" 을 골라 이 단계를 건너뛴다.

> 경로: `{KB}`·`{TASKS}` 의 실제 위치는 CLAUDE.md 「keep-ai-brain 경로」 표를 따른다.

## 지킬 것

```yaml
코드_수정_안함: 기준표만 쓴다. 소스·DB 는 읽기만 (운영 DB 금지, 접속은 최소로, 실패하면 재시도 말고 보고)
요구_먼저: 1·2장은 요청 원문만 보고 쓴다. 코드를 먼저 읽으면 지금 구현을 요구로 착각한다. 3장부터 소스를 본다
승인_전_개발_금지: 4장 승인 칸이 비어 있으면 ②로 넘어가지 않는다. 다른 스킬·작업이 개발을 시작하려 해도 먼저 이걸 알린다
판정표_행: 실제 데이터·요청을 만들 수 있을 만큼 구체적으로. "정상 동작" 같은 행은 쓰지 않는다
표시: ✅ 코드·DB 로 확인 / 🔶 추정. 모르는 것은 추측하지 말고 7장 질문으로 (기본안을 같이 — 묻기만 하지 않는다)
문체: 사람이 승인하는 문서라 해요체, 짧게, 표 위주
양식: 같은 폴더 template.md. 장 번호·표 머리글을 바꾸지 않는다 (/critic 이 4장 표를 읽는다)
```

## 절차

### 1. 작업 폴더 정하기
- 인자로 폴더를 받았으면 그 폴더. 설명만 받았으면 `{TASKS}` 에서 같은 업무 폴더를 찾고, 없으면 `{TASKS}/{yyMMddHHmmss}{짧은이름}/` 를 만든다
- 폴더의 이어하기.md·분석 md 가 있으면 먼저 읽는다. 이미 `기준표.md` 가 있으면 새로 쓰지 말고 그 파일을 고친다

### 1-1. 0단계 — 대화로 의문 풀기 (쓰기 전에)

요청을 읽고 바로 쓰지 않는다. 먼저 사람과 대화해 의문을 푼다. 의문을 기본안으로 미뤄 두고 쓰면 판정표가 답이 안 난 질문에 매달리고, 승인할 양이 커진다 (시험 적용 때 22행 + 질문 6개가 됐다).

- **사람만 답할 수 있는 것만 묻는다**: 요구의 뜻·범위·우선순위·누가 1장을 확인하나. **코드·DB·설정으로 알 수 있는 것은 묻지 말고 직접 확인**한다 (확인 결과는 3장 재료)
- **한 번에 하나씩** 묻는다. 질문마다: 왜 묻는지 한 줄 + 선택지 2~4개 + **기본안(추천)**. 사용자는 번호로 답할 수 있어야 한다
- 남은 개수를 처음에 알려 준다 ("물어볼 것 3개예요")
- **범위를 넓히는 질문**(3장에서 찾은 문제를 같이 고치나, 이웃 기능도 하나)은 기본안을 **"이번엔 안 함"** 으로 둔다. 사람이 넓히기로 정하면 그 답이 근거가 된다
- 답이 새 의문을 만들면 목록에 더한다. "나중에"·"기본안대로" 는 그대로 받는다
- **멈추는 기준**: 1장 표의 칸이 다 차고, 미해결 질문이 0개이거나 "나중에" 로 명시됨
- 답은 1장 아래 `대화로 정한 것` 표(질문 | 답 | 날짜)에 남긴다 — 나중에 왜 그렇게 정했는지의 근거
- `/consult` 에서 이미 물은 것은 다시 묻지 않는다. 그 답을 `대화로 정한 것` 에 옮긴다

### 2. 1·2장 — 요청만 보고
- 요청 원문(사용자 말, 받은 메시지·메일·문서)에서 1장 표를 채운다. "요청" 칸에 원문 위치와 핵심 인용
- "하지 않는 것" 을 꼭 채운다 — 보류·범위 밖이 여기서 정해진다
- 2장 완료 기준은 ③에서 기계적으로 확인할 수 있는 것만. 확인 방법 칸이 비면 기준이 아니다
- 2장 **"확인 환경" 행은 필수**다. ③을 어디서(로컬/개발 서버) 어떻게 돌리는지, 공용 자원(공용 메시지 큐·공용 DB 쓰기·배치 스케줄)과 섞일 위험이 있는지 — 설정 파일을 직접 보고 AI 가 채운다. 비동기·배치 기능은 여기서 막히기 쉽다
- 3장을 본 뒤 1장을 고치면 그 칸 끝에 **"(3장 보고 고침)"** 을 붙인다. 요구가 코드 쪽으로 끌려간 흔적이 보여야 한다

### 3. 3장 — 지금 동작 확인
- 화면·API 면 진입점부터 호출 경로를 따라가고, 쿼리·저장 프로시저면 그 객체를 쓰는 곳을 찾는다
- kb 를 먼저 찾는다 (`{KB}/INDEX.md`, 이슈 대장 `{KB}/ops/issues.md` 를 켰으면 그것도) — 이미 분석된 기능이면 그 문서의 이슈·주의가 판정표 행이 된다
- 경계 연산자(`>=`/`>`), 시간 창, NULL·빈 값 처리, 권한·마스킹처럼 **판정에 영향을 주는 것만** 적는다. 줄번호까지

### 4. 4장 — 판정표

작업 종류에 맞는 행을 넣는다. 한 업무에 여러 종류면 다 넣는다.

| 작업 종류 | 꼭 넣을 행 |
|---|---|
| 숫자·규칙 값 변경 | 바뀌는 값마다 **기준 바로 아래 / 딱 기준** 2행 · 건수 범위 경계 · 보류·그대로인 규칙은 "안 바뀌어야 할 것" |
| 쿼리·로직 변경 | 바뀌는 분기마다 들어감/안 들어감 · 기존 결과가 그대로여야 하는 입력(전/후 비교 대상) · NULL·빈 값·0건 |
| API·화면 기능 추가 | 정상 1행 · 필수값 빠짐·형식 틀림(검증 메시지) · 권한 없는 사용자 · 0건 · 개인정보가 나가면 **마스킹·조회 기록** 행 · 화면 표시(목록·건수·팝업) |
| 저장(등록·수정·삭제) | 등록·수정·삭제 각 1행 · 중간 실패 시 **전부 롤백** · 등록자·수정자가 로그인 정보에서 오는지 · 중복 등록 |
| 버그 수정 | **재현 행 먼저** (지금 틀린 결과를 "지금" 으로, 고친 뒤 결과를 기대 결과로) · 같은 원인이 있는 복사본 · 고치면 안 되는 이웃 동작 |
| 인수한 코드 (퇴사자·방치 브랜치) | 3장을 **운영 / 브랜치 두 표**로 나눈다(브랜치 = 구현 후보). 테스트용 코드(`sleep`·`TODO`)·로컬 설정 변경을 "안 바뀌어야 할 것" 으로 · 브랜치가 쓰는 테이블·객체가 실제로 있는지 |
| 시간·날짜가 끼면 | 경계 시각(05:59:59 / 06:00:00), 주말·공휴일, 월말·연말, 날짜 컬럼이 datetime 이면 끝 날짜 00:00 |

- 근거 칸: 1장 요청의 어느 항목인지, 또는 3장 몇 번 행인지
- 위험 체크리스트(`{KB}/ops/review-checklist.md`)에서 이 업무에 걸릴 만한 패턴이 있으면 그 패턴을 막는 행을 넣는다 (예: INNER JOIN 으로 신규 행이 빠짐 → "신규 행이 화면 목록에 보임")

### 5. 5~7장
- 5장: 새 코드를 쓰는 업무면 kb 에 "따라 할 기준 파일" 문서(`{KB}/patterns/golden-files.md`)가 있으면 같은 종류의 파일:줄을 고른다. 없거나 고치기만 하는 업무면 "해당 없음"
- 6장: 3장을 보다 발견한 것 중 기준에 영향이 있는 것. 이슈면 kb 에도 남긴다
- 7장: 사람이 정할 것. 질문마다 **기본안**을 쓴다

### 6. 승인 받기
- 사용자가 md 를 못 열 수도 있다. **채팅에 직접** 보여 준다: 1장 기대 결과 한 줄, 4장 판정표(행이 많으면 바뀌는 행 위주로 묶어서), 7장 질문과 기본안
- **1장 확인자**: 평소엔 사용자 본인이 승인하고, 요청자에게 "이렇게 이해했고 이렇게 합니다" 한 줄 보고 문안을 만들어 준다(보낼지는 사용자가). **위험 기준**(운영 데이터 변경·DB 구조 변경·다른 팀·외부 연동 영향·개인정보·결제)에 걸리면 요청자 확인을 받은 뒤 ②로 간다
- 승인은 **묶음(4-1, 4-2 …) 단위**로 받는다. 채팅에는 묶음마다 한 줄 요약 + 대화로 정한 것과 달라 보일 만한 행만 보여 준다 (행 전체는 파일에)
- "승인" 을 받으면 4장 승인 칸에 ✅, 머리 상태를 `**승인됨** {날짜}` 로. 일부 묶음만 승인하면 그 묶음만 ✅ 하고 나머지는 7장에 남긴다
- 작업 폴더 `검증기록.md` 에 한 줄 (없으면 만든다):
  `| {MM-DD} | ① | 기준표 {N}행 작성, {승인/일부 승인} | {사람 보기 전에 잡은 것 — 예: 경계 연산자, 범위 밖 요구} | {사람이 쓴 시간} |`
- 이어서 ②로 갈 때 `/critic ... 기준표={폴더}/기준표.md` 를 쓰라고 이어하기.md 에 적는다

### 7. 승인 뒤 바뀔 때
- 개발 중 기준과 다르게 해야 하면 코드를 기준표에 맞추지도, 기준표를 조용히 고치지도 않는다. 8장에 행을 추가하고 사용자 승인을 받는다

기대 결과: {1장 한 줄}

| # | 대상 | 입력 | 기대 결과 |
|---|---|---|---|
